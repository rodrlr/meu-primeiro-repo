Os termos que aparecem o tempo todo

repositório
A pasta de um projeto hospedada no GitHub. Tudo acontece dentro de um. Também chamado de repo.
commit
Uma versão salva. Guarda o que mudou, quem mudou, quando e por quê. Nada se perde, dá para voltar a qualquer commit anterior.
mensagem
O texto que você escreve ao salvar. É o que vai aparecer no histórico daqui a seis meses, então descreva a mudança, não o arquivo.
branch
Uma linha paralela de trabalho. Serve para mexer sem afetar a versão boa.
main
O nome da branch principal, a versão oficial. Enquanto você trabalha sozinho, só ela basta.
README.md
O arquivo de apresentação. O GitHub mostra o conteúdo dele formatado embaixo da lista de arquivos, na entrada do repositório.
issue
Uma anotação de pendência, erro ou ideia. Funciona como lista de tarefas do projeto, e qualquer pessoa pode abrir uma.
fork
Uma cópia do repositório de outra pessoa dentro da sua conta, para você mexer sem tocar no original.
pull request
Um pedido para que suas mudanças entrem no projeto de outra pessoa. Abre uma tela de discussão antes de qualquer coisa ser aceita.
clone
Baixar o repositório para o computador mantendo a ligação com o GitHub, para enviar e receber mudanças. Exige o programa Git instalado.
star
Favoritar um projeto. Vira sua estante de coisas para achar de novo depois.
GitHub Pages
O serviço que transforma os arquivos HTML do repositório num site com endereço público.

Onde cada coisa fica na tela

  • Abas no topo do repositório. Code são os arquivos, Issues as anotações, Pull requests as propostas de mudança, Settings as configurações.
  • Botão Add file. Fica na mesma linha da caixa Go to file, à esquerda do botão verde Code. Com a janela estreita ele encolhe e vira só um sinal de +.
  • Botão verde Code. É por onde se baixa o projeto, com a opção Download ZIP.
  • Contagem de commits. O relógio com um número, acima da lista de arquivos, tipo 2 Commits. É a porta do histórico.
  • Painel About. Coluna da direita, com a descrição, a licença e os temas do projeto.
  • Publicação. Settings › Pages, no menu da esquerda.

Criar um repositório

  1. Sinal de + no canto superior direito do site, depois New repository.
  2. Em Repository name, um nome sem espaços e sem acento, com hífen no lugar do espaço.
  3. Escolha Public ou Private. Privado só você vê, e serve para material interno.
  4. Marque Add a README file para o repositório já nascer com uma apresentação.
  5. Create repository.

O endereço do repositório é sempre github.com/seu-usuario/nome-do-repo. Dá para digitar direto no navegador, sem procurar por menus.

Salvar uma versão

Há três formas de colocar conteúdo lá dentro, todas no botão Add file da página inicial do repositório, exceto a terceira.

  • Upload files abre uma área para arrastar arquivos do seu computador. É o caminho do dia a dia para mandar um .py, um .sql ou um .html que já existe.
  • Create new file cria um arquivo em branco direto no navegador.
  • O ícone de lápis, ao abrir um arquivo já existente, edita o conteúdo ali mesmo.

Em qualquer um dos três, o salvamento é o mesmo: botão verde Commit changes, troque a mensagem automática por uma descrição da mudança, mantenha Commit directly to the main branch e confirme.

Ver o que mudou

Clique na contagem de Commits e depois na mensagem que te interessa. Aparece a comparação linha a linha, vermelho para o que saiu e verde para o que entrou.

README.md

- # meu-primeiro-repo+ # Meu primeiro repositório++ Estou aprendendo a usar o GitHub.

O sinal de menos é a linha antiga, o de mais é a nova. Linhas sem sinal ficaram iguais.

É esse registro que substitui a pasta cheia de relatorio_v2_final_agora_vai.py. Um arquivo só, com todas as versões anteriores recuperáveis e cada uma explicada por quem a salvou.

Publicar uma página HTML

  1. Coloque no repositório um arquivo chamado exatamente index.html. O nome importa, é ele que o serviço procura como página de entrada.
  2. Vá em Settings, e no menu da esquerda clique em Pages.
  3. Em Source, deixe Deploy from a branch.
  4. Em Branch, troque None por main e deixe o seletor ao lado em / (root).
  5. Save. A frase confirmando que o site está sendo construído aparece logo acima.
  6. Espere um ou dois minutos e recarregue a página. O endereço aparece no topo da seção, no formato seu-usuario.github.io/nome-do-repo/.

Duas limitações. O Pages serve apenas páginas estáticas, ou seja, HTML, CSS, JavaScript e arquivos de dados. Nada que precise rodar no servidor, como Python, PHP ou consultas a banco.

E se o repositório é público, qualquer pessoa com o link vê a página, mesmo que ela não apareça no Google. Material sensível não vai para um repositório público.

Erro 404 logo depois de salvar costuma ser só a construção que ainda não terminou. Espere e recarregue. Se insistir, confirme que o arquivo se chama index.html e está na raiz do repositório, não dentro de uma subpasta.

Para atualizar o site depois, basta enviar uma nova versão do arquivo e fazer o commit. A publicação refaz sozinha em um ou dois minutos.

Pesquisar projetos

A busca fica na barra do topo. O que muda o resultado é usar filtros, escritos colados com dois pontos e sem espaço depois. Vários filtros na mesma linha se somam.

FiltroO que faz
language:pythonSó projetos naquela linguagem
stars:>500Corta o que ninguém usa
topic:dashboardTema declarado pelo próprio autor do projeto
in:name streamlitA palavra precisa estar no nome do repositório
in:readme cooperativaA palavra precisa estar no texto de apresentação
pushed:>2026-01-01Só o que teve movimento desde essa data
license:mitSó o que tem licença de uso liberada

Na página de resultados, as abas da esquerda mudam o que está sendo procurado. Repositories busca projetos inteiros e resolve quase tudo. Code busca dentro dos arquivos, útil quando você quer ver como alguém escreveu um trecho específico.

Avaliar se um projeto presta

Abra o repositório e olhe nesta ordem, que vai do sinal mais barato ao mais caro de verificar.

  1. Data do último commit. O texto cinza no canto direito da lista de arquivos. Projeto parado há anos costuma quebrar com bibliotecas atuais.
  2. README. Se não explica como instalar e não mostra um exemplo de uso, vai te custar caro.
  3. Issues. Centenas abertas sem resposta há meses significa que ninguém está cuidando daquilo.
  4. Licença, no painel About à direita. MIT e Apache 2.0 liberam uso e modificação. Repositório sem licença nenhuma, tecnicamente, não dá permissão de uso, o que pesa quando é para uso institucional.
  5. Estrelas. Dizem popularidade, não qualidade. Servem para ordenar resultados, não para decidir.

Pegar o código para o seu computador

  • Download ZIP, dentro do botão verde Code, baixa a pasta inteira. Funciona sempre e não exige instalar nada.
  • Se for uma biblioteca Python, o caminho normal não é baixar do GitHub, é rodar pip install nome-da-biblioteca. O repositório serve para ler o código, a documentação e as issues antes de instalar.
  • Fork, no topo direito, copia o projeto para a sua conta quando você quer modificar e manter a sua versão.

O que vem depois

Tudo neste guia é feito pelo navegador, sem instalar nada. Os três passos seguintes, quando fizerem falta:

  • Git no computador. O programa que faz commits sem passar pelo site, útil quando são muitos arquivos ou quando você quer versionar enquanto trabalha.
  • Branch e pull request. O fluxo de trabalhar em paralelo e revisar antes de juntar, que é o que faz sentido quando mais de uma pessoa mexe no mesmo projeto.
  • Repositório privado com colaboradores. Em Settings, a opção de dar acesso a pessoas específicas sem abrir o conteúdo para o mundo.
